## 변경 배경

이 커밋은 L3 학생 대시보드의 데이터 해석 도우미 챗봇(`DataHelperChatbot`)이 기존의 단일 `callAI()` 직접 호출 방식에서 `agentChat()` (POST /chat) 기반의 에이전트 아키텍처로 전환됨에 따른 마이그레이션입니다.

- **목적**: 기존 `callAI()` 직접 호출에서 `agentChat()` (에이전트 API)로 전환. 학생 데이터 컨텍스트를 시스템 프롬프트에 주입하고, 질문만 별도로 전송하는 구조로 개선
- **도메인**: 비즈니스 로직 (AI 프롬프트 엔지니어링 / API 연동)
- **변경 방향**:
  - 기존: `buildPromptForQuestion()` 하나로 데이터+질문을 합쳐서 하나의 user message로 전송
  - 변경: `buildStudentContextMarkdown()`으로 학생 데이터를 마크다운으로 분리하여 `context_data.context`에 주입하고, `buildQuestion()`은 순수 질문 지시문만 반환하여 `text`로 전송
  - type-* 질문에 한해 `context_data.profile`에 schoolLevel/predictedType을 추가로 전달

## [GOOD] 잘된 점

### 1. 관심사 분리(SoC)가 명확함

`buildStudentContextMarkdown`과 `buildQuestion`을 완전히 분리하여 각각의 역할이 명확해졌습니다. 기존에는 `buildPromptForQuestion` 하나가 데이터와 질문을 모두 포함했으나, 이제는 시스템 컨텍스트와 사용자 메시지가 분리되어 에이전트 아키텍처에 적합합니다.

```typescript
// 변경 후: getDataHelperAnswer 내부
const questionText = buildQuestion(questionId, data);       // 질문 지시문만
const studentContext = buildStudentContextMarkdown(data);    // 학생 데이터 컨텍스트
const contextData = {
  context: `${SYSTEM_PROMPT_DATA_HELPER}\n\n---\n\n${studentContext}`,
  ...(questionId.startsWith('type-') && {
    profile: { schoolLevel: data.schoolLevel, predictedType: data.predictedType },
  }),
};
const response = await agentChat(questionText, sessionId, contextData);
```

`agentChat` 함수의 시그니처(`agentApiService.ts` 42-44행)를 보면 세 번째 파라미터로 `contextData?: Record<string, unknown> | null`을 받으며, 내부적으로 `AgentQuery` 객체의 `context_data` 필드로 직렬화되어 API에 전송됩니다. 이 구조는 에이전트가 시스템 프롬프트(컨텍스트)와 사용자 메시지(질문)를 분리해서 처리할 수 있게 합니다.

### 2. 중복 제거로 코드 간결화

기존에는 `buildDiagnosisStrengths`, `buildDiagnosisWeaknesses`, `buildTypeIndividual` 등이 각각 `subResults`와 `subContext`를 파라미터로 받아 내부에서 다시 가공했습니다. 변경 후에는 모든 데이터 가공이 `buildStudentContextMarkdown`에서 한 번만 수행되고, 질문 빌더들은 파라미터 없이 순수 문자열 템플릿만 반환합니다.

```typescript
// 변경 전: 각 빌더가 데이터를 파라미터로 받아 재가공
const buildDiagnosisStrengths = (subResults: SubCategoryResult[], subContext: string): string => {
  const strengths = filterStrengths(subResults);
  const strengthContext = formatResultList(strengths, '...');
  return `...${strengthContext}...${subContext}...`;
};

// 변경 후: 데이터는 buildStudentContextMarkdown에서만 처리, 질문 빌더는 순수 템플릿
const buildDiagnosisStrengths = (): string =>
  `위 학생 컨텍스트의 강점 영역을 **구체적으로 분석**해 주세요.
- 각 강점 영역별 의미와 장점 설명
- ...`;
```

이로 인해 각 빌더 함수의 시그니처가 `(subResults, subContext)`에서 `()`로 단순화되었고, `buildQuestion`의 `builders` 맵에서도 일관된 형태(`() => string`)로 관리할 수 있게 되었습니다.

### 3. 일관된 에러 처리 유지

`getDataHelperAnswer`의 반환 타입(`Promise<string>`)과 `agentChat`의 응답에서 `response.response`를 추출하는 방식이 일관되게 유지되어, 호출부(`DataHelperChatbot`)에 미치는 영향을 최소화했습니다.

```typescript
// agentApiService.ts 67행: AgentChatResponse 타입
export interface AgentChatResponse {
  response: string;
  session_id: string;
  history_count: number;
}

// dataHelperService.ts: response.response 추출
const response = await agentChat(questionText, sessionId, contextData);
return response.response;
```

### High (우선 수정 권장)

**1. `buildTypeOverview`의 `predictedType` 파라미터 전달 방식 일관성 부족**

`buildQuestion`의 `builders` 맵에서 `type-1`만 `() => buildTypeOverview(data.predictedType)`로 래핑되어 있고, `type-2`와 `type-3`는 파라미터 없는 함수 참조를 직접 전달합니다. `buildTypeOverview`만 유일하게 `predictedType`을 파라미터로 받는데, 이는 다른 빌더들과 일관성이 없습니다.

```typescript
// dataHelperService.ts 195-201행
const builders: Record<QuestionId, () => string> = {
  'diagnosis-1': buildDiagnosisOverview,
  'diagnosis-2': buildDiagnosisFactors,
  'diagnosis-3': buildDiagnosisStrengths,
  'diagnosis-4': buildDiagnosisWeaknesses,
  'type-1': () => buildTypeOverview(data.predictedType),  // 유일하게 래핑
  'type-2': buildTypeDetail,
  'type-3': buildTypeIndividual,
};
```

`buildTypeOverview`의 현재 구현을 보면:

```typescript
const buildTypeOverview = (predictedType: StudentType): string =>
  `위 학생 컨텍스트의 학교급별 전체 유형 정보를 참고하여, **3가지 유형 전체의 특징을 비교하며 설명**해 주세요.
- 각 유형별 핵심 특성 요약
- 유형 간 차이점 비교
- 각 유형에 효과적인 교사 접근법
- 분류된 유형(${predictedType})은 어떤 위치인지 마지막에 언급`;
```

`${predictedType}`이 템플릿 리터럴에 포함되어 있어 파라미터가 필요합니다. 그러나 `buildStudentContextMarkdown`에 이미 유형 정보(분류 유형, 확률, 설명)가 모두 포함되어 있으므로, 이 정보는 질문 템플릿에서 중복됩니다. `buildStudentContextMarkdown`의 출력을 보면:

```
## 학생 기본 정보
- 학교급: ${data.schoolLevel}
- 분류 유형: ${data.predictedType} (확률 ${typeProb}%)
${typeInfo ? `- 유형 설명: ${typeInfo.description}` : ''}
...
## 학교급별 전체 유형 정보 (${data.schoolLevel})
${allTypesInfo}
```

이미 유형명과 설명이 컨텍스트에 포함되어 있으므로, `buildTypeOverview`에서 `predictedType`을 파라미터로 받아 질문에 포함시킬 필요가 없습니다. 다음과 같이 통일하는 것이 좋습니다:

```typescript
const buildTypeOverview = (): string =>
  `위 학생 컨텍스트의 학교급별 전체 유형 정보를 참고하여, **3가지 유형 전체의 특징을 비교하며 설명**해 주세요.
- 각 유형별 핵심 특성 요약
- 유형 간 차이점 비교
- 각 유형에 효과적인 교사 접근법
- 분류된 유형은 어떤 위치인지 마지막에 언급`;
```

이렇게 하면 `builders` 맵에서도 일관되게 `'type-1': buildTypeOverview`로 사용할 수 있습니다.

**영향 분석**: 이 변경은 AI가 받는 질문 텍스트에서 "분류된 유형(${predictedType})"이라는 구체적 유형명이 제거되는 효과가 있습니다. 하지만 컨텍스트(`buildStudentContextMarkdown`)에 이미 유형 정보가 포함되어 있으므로, AI가 유형명을 추론하는 데 문제가 없을 것으로 판단됩니다. 오히려 질문이 더 일반화되어 다른 질문 빌더들과 일관성을 유지할 수 있습니다.

### Medium (개선 권장)

**1. `buildStudentContextMarkdown` 내 `schoolData` 타입 안전성**

`LPA_PROFILE_DATA[data.schoolLevel]`의 결과가 `undefined`일 경우 `schoolData.types`에 접근할 때 런타임 에러가 발생할 수 있습니다.

```typescript
// dataHelperService.ts 93-94행
const schoolData = LPA_PROFILE_DATA[data.schoolLevel];
const allTypesInfo = schoolData.types  // schoolData가 undefined면 TypeError
    .map((t) => { ... })
```

`data.schoolLevel`의 타입이 `SchoolLevel`로 정의되어 있지만, 런타임에 예상치 못한 값이 전달될 가능성을 고려하면 방어 코드를 추가하는 것이 안전합니다:

```typescript
const schoolData = LPA_PROFILE_DATA[data.schoolLevel];
if (!schoolData) {
  return `## 학생 기본 정보\n- 학교급: ${data.schoolLevel}\n- 분류 유형: ${data.predictedType} (확률 ${typeProb}%)\n\n## 유형 정보\n- 학교급 "${data.schoolLevel}"에 대한 프로필 데이터를 찾을 수 없습니다.`;
}
const allTypesInfo = schoolData.types.map((t) => { ... });
```

**2. `buildStudentContextMarkdown` 함수의 단일 책임 원칙 위반 가능성**

`buildStudentContextMarkdown`은 약 50줄에 달하는 단일 함수로, 다음과 같은 여러 책임을 포함하고 있습니다:
- 학생 기본 정보 포맷팅
- 11개 중분류 T점수 포맷팅
- 강점/약점 영역 포맷팅
- 유형 평균 대비 개인 편차 포맷팅
- 학교급별 전체 유형 정보 포맷팅
- 유형 확률 분포 포맷팅

현재 단계에서는 각 섹션이 간결하게 유지되고 있어 과도한 추상화는 오히려 가독성을 해칠 수 있습니다. 함수가 더 커지거나 각 섹션의 로직이 복잡해질 때 별도 헬퍼 함수로 분리하는 것을 고려하세요.
