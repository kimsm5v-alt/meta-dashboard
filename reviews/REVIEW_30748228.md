### 1. `frontend/src/shared/store/useCaptureStore.ts`

**변경 내용**:
- `CaptureState` 인터페이스에 `bottomRightFabCount: number`, `registerBottomRightFab: () => void`, `unregisterBottomRightFab: () => void` 추가
- 초기값 `bottomRightFabCount: 0`
- `registerBottomRightFab`: 카운트 +1
- `unregisterBottomRightFab`: 카운트 -1 (음수 방지를 위해 `Math.max(0, ...)` 적용)

**[PROBLEM] reset() 함수가 bottomRightFabCount를 초기화하지 않음**

- **위치**: 라인 47
- **기존 코드**:
```typescript
reset: () => set({ overlayOpen: false, pendingImage: null, pendingMeta: null }),
```
- **해결 방안 (수정 코드)**:
```typescript
reset: () => set({ overlayOpen: false, pendingImage: null, pendingMeta: null, bottomRightFabCount: 0 }),
```
- **위험도**: High
- **영향**: `AuthContext.tsx`(라인 150)에서 로그아웃 시 `useCaptureStore.getState().reset()`을 호출합니다. 이때 `bottomRightFabCount`가 초기화되지 않아, 다음 사용자가 로그인했을 때 이전 사용자의 FAB 카운트가 남아있어 `FloatingCaptureButton`의 위치가 잘못 계산됩니다. `DataHelperChatbot`이 없는 페이지에서도 `$raised`가 `true`로 유지되어 캡처 버튼이 비정상적인 위치에 렌더링됩니다.

**재현 시나리오**:
1. 사용자 A가 학생 대시보드(`DataHelperChatbot` 마운트)에서 로그아웃
2. 사용자 B가 로그인하여 `DataHelperChatbot`이 없는 페이지(예: AI Room)로 이동
3. `bottomRightFabCount`가 1로 남아 있어 `FloatingCaptureButton`이 `$raised=true` 상태로 렌더링
4. 캡처 버튼이 `right: 1.625rem, bottom: 5.75rem`에 위치하여 의도치 않은 위치에 표시됨

**[GOOD] 잘된 점**:
- `unregisterBottomRightFab`에서 `Math.max(0, ...)`로 음수 방지 처리
- `register`/`unregister` 쌍을 `useEffect` 클린업 패턴에 맞게 설계
- JSDoc 주석으로 각 함수의 용도를 명확히 문서화

### 2. `frontend/src/features/student-dashboard/ui/DataHelperChatbot.tsx`

**변경 내용**:
- `useCaptureStore` import 추가
- 컴포넌트 마운트 시 `registerBottomRightFab()`, 언마운트 시 `unregisterBottomRightFab()`을 호출하는 `useEffect` 추가 (라인 155-160)

**[PROBLEM] React 18 Strict Mode에서 useEffect 이중 호출 문제**

- **위치**: 라인 155-160
- **기존 코드**:
```typescript
useEffect(() => {
  const { registerBottomRightFab, unregisterBottomRightFab } = useCaptureStore.getState();
  registerBottomRightFab();
  return () => unregisterBottomRightFab();
}, []);
```
- **위험도**: Medium
- **영향**: React 18 Strict Mode에서는 `useEffect`가 마운트-언마운트-마운트 순서로 두 번 실행됩니다. 이 경우 `registerBottomRightFab()`이 두 번 호출되고, 언마운트 시 `unregisterBottomRightFab()`이 한 번만 호출되어 `bottomRightFabCount`가 1이 아닌 2가 됩니다. Strict Mode는 개발 환경에서만 동작하므로 프로덕션에는 영향이 없지만, 개발 중 테스트 시 혼란을 줄 수 있습니다.

**수정 코드 제시 불가 — 문맥 파악 불충분**: Strict Mode 이중 호출을 완전히 방지하려면 `useRef`로 마운트 상태를 추적하거나, `registerBottomRightFab` 내부에서 중복 호출을 방지하는 로직이 필요합니다. 하지만 이는 현재 코드의 의도(단순 카운터)와 맞지 않을 수 있어, 정확한 수정 코드를 제시하기보다는 인지하고 있어야 할 위험으로 표시합니다.

**[GOOD] 잘된 점**:
- `useCaptureStore.getState()`를 사용하여 `useEffect` 내부에서 직접 스토어 함수에 접근 — selector 구독 없이 일회성 호출이므로 불필요한 리렌더링을 유발하지 않음
- 클린업 함수에서 `unregisterBottomRightFab()`을 반환하여 언마운트 시 자원 정리

### 3. `frontend/src/widgets/screen-capture/FloatingCaptureButton.tsx`

**변경 내용**:
- `Button` 스타일드 컴포넌트에 `$raised: boolean` prop 추가
- `$raised`가 `true`일 때 `right: 1.625rem`, `bottom: 5.75rem`으로 위치 변경
- `bottomRightFabCount`를 Zustand에서 구독하여 `$raised` prop에 전달

**[PROBLEM] z-index 불일치 — FabButton(z-index: 50) vs FloatingCaptureButton(z-index: sticky=1020)**

- **위치**: 라인 15
- **기존 코드**:
```typescript
z-index: ${({ theme }) => theme.zIndex.sticky};
```
- **위험도**: High
- **영향**: `DataHelperChatbot`의 `FabButton`은 `z-index: 50`이고, `FloatingCaptureButton`은 `z-index: 1020(sticky)`입니다. `$raised`가 `true`일 때 `FloatingCaptureButton`이 `DataHelperChatbot` 위에 위치하도록 설계되었는데, z-index 차이가 970이나 나므로 `DataHelperChatbot`의 `ChatPanel`(z-index: 50)도 `FloatingCaptureButton` 아래에 위치하게 됩니다. `ChatPanel`이 열려 있을 때 `FloatingCaptureButton`이 챗봇 패널 위에 떠 있게 되어 UX에 혼란을 줄 수 있습니다.

**수정 코드 제시 불가 — 문맥 파악 불충분**: `ChatPanel`의 z-index와 `FloatingCaptureButton`의 z-index 간의 관계를 정확히 파악하려면 전체 레이아웃 구조와 의도된 동작(챗봇 패널 위에 캡처 버튼이 떠 있어야 하는지)을 확인해야 합니다. 이는 디자인 의도에 따라 결정되어야 할 사항입니다.

**[PROBLEM] 하드코딩된 위치 값 — DataHelperChatbot의 FAB 스타일과 강한 결합**

- **위치**: 라인 13-14
- **기존 코드**:
```typescript
right: ${({ $raised, theme }) => ($raised ? '1.625rem' : theme.spacing.xl)};
bottom: ${({ $raised, theme }) => ($raised ? '5.75rem' : theme.spacing.xl)};
```
- **위험도**: Medium
- **영향**: `DataHelperChatbot`의 `FabButton` 크기(3.5rem)나 위치(right 1.5rem)가 변경되면 `FloatingCaptureButton`의 위치가 어긋나 두 버튼이 겹치거나 간격이 벌어집니다. 주석에 계산식이 상세히 기록되어 있어 비교적 추적이 용이하지만, 자동 동기화 메커니즘은 없습니다.

**[GOOD] 잘된 점**:
- 주석에 위치 계산 과정을 상세히 문서화하여 유지보수성을 높임
- `$raised` prop을 transient prop(`$` 접두사)으로 사용하여 DOM으로 전달되지 않도록 함
- `bottomRightFabCount`를 selector로 구독하여 불필요한 리렌더링을 방지
