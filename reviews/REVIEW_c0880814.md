## [GOOD] 잘된 점

**1. 2단계 은퇴 전략(rename -> 추후 DROP)**

컬럼을 바로 DROP하지 않고 이름 변경 후 NULLABLE로 전환하는 방식은 운영 안정성 측면에서 모범적인 접근입니다. 문제 발생 시 롤백이 가능하고, 데이터가 보존되므로 부담 없이 안정화 기간을 가질 수 있습니다. SQL 파일 상단의 정책 섹션에서 이 전략을 명확히 문서화한 점도 좋습니다.

```sql
-- 정책:
--   - 본 SQL 적용 후 1~수주간 안정화 모니터링.
--   - 문제 없으면 → `02-pii-column-drop.sql` 의 진짜 DROP 으로 별도 일정에 마무리.
--   - 문제 있으면 → 본 파일 하단의 ROLLBACK 섹션으로 즉시 복구 (적용 직후 한정).
```

**2. DROP INDEX를 CHANGE COLUMN보다 먼저 배치**

UNIQUE 인덱스가 있는 컬럼(email)을 변경하기 전에 인덱스를 먼저 해제하는 순서가 정확합니다. MySQL에서 UNIQUE 인덱스에 의존하는 컬럼을 변경하려면 인덱스 해제가 선행되어야 합니다. 주석으로 이 이유를 명시한 점도 좋습니다.

```sql
-- 주의: DROP INDEX 를 CHANGE COLUMN 앞에 둔다 (UNIQUE 인덱스 의존 컬럼 먼저 해제).
ALTER TABLE `user`
  DROP INDEX uk_user_email,
  CHANGE COLUMN email    email_legacy_20260530    VARCHAR(100) NULL,
  ...
```

**3. 사전 확인(Step 2) + 적용 후 검증(Step 4) 포함**

단순히 ALTER만 실행하는 것이 아니라, 적용 전 인덱스/컬럼 상태를 확인하고 적용 후 데이터 보존 여부를 검증하는 SELECT 쿼리까지 포함하여 운영자의 실수를 방지합니다. 특히 데이터 보존 확인 쿼리는 `SUM(IS NOT NULL)`을 사용하여 기존 데이터가 100% 보존되었는지 검증하는 점이 실용적입니다.

```sql
-- ③ 데이터 보존 확인 (기존 행의 값은 그대로 유지됨)
SELECT
    COUNT(*)                                       AS total_users,
    SUM(email_legacy_20260530    IS NOT NULL)      AS email_kept,
    SUM(nickname_legacy_20260530 IS NOT NULL)      AS nickname_kept
FROM `user`;
```

**4. 롤백 SQL을 동일 파일에 포함**

별도 문서를 찾을 필요 없이 동일 파일 하단에 롤백 SQL을 주석으로 포함시킨 점이 실용적입니다. 또한 롤백의 제약 조건(NULL 행이 없을 때만 안전)을 명확히 문서화하여 운영자의 판단을 돕습니다.

### High (우선 수정 권장)

**1. `user` 테이블 `gender` 컬럼의 롤백 시 NULL 처리 불일치**

- **위치 (라인 번호)**: 130-131
- **기존 코드**:
```sql
-- ALTER TABLE `user`
--   CHANGE COLUMN email_legacy_20260530    email    VARCHAR(100) NOT NULL,
--   CHANGE COLUMN nickname_legacy_20260530 nickname VARCHAR(50)  NOT NULL,
--   CHANGE COLUMN gender_legacy_20260530   gender   VARCHAR(10)  NULL,
```

- **문제점**: 롤백 시 `gender` 컬럼은 `NULL`로 복구되는데, 원본 `gender` 컬럼이 원래 `NULL`이었는지 `NOT NULL`이었는지 SQL 파일 내에 명시되어 있지 않습니다. 만약 원본이 `NOT NULL`이었다면 롤백 후에도 `NULL` 허용 상태로 남아 기존 NOT NULL 제약 조건이 영구히 소실됩니다. `group_member`의 `gender`와 `email`도 동일한 문제가 있습니다.

- **해결 방안**: SQL 파일 상단에 각 컬럼의 원본 NULLABLE 상태를 주석으로 명시하거나, 롤백 SQL에서 원본 제약 조건을 정확히 복원하도록 수정합니다. Step 2의 `SHOW COLUMNS` 결과에서 `IS_NULLABLE` 값을 기록해두고 롤백 SQL에 반영해야 합니다.

**2. `group_member.email` 롤백 시 UNIQUE 인덱스 복원 누락 가능성**

- **위치 (라인 번호)**: 133-136
- **기존 코드**:
```sql
-- ALTER TABLE group_member
--   CHANGE COLUMN nickname_legacy_20260530 nickname VARCHAR(50)  NOT NULL,
--   CHANGE COLUMN email_legacy_20260530    email    VARCHAR(255) NULL,
--   CHANGE COLUMN gender_legacy_20260530   gender   VARCHAR(10)  NULL,
--   ADD KEY idx_gm_email (email);
```

- **문제점**: `user` 테이블의 `email`은 `UNIQUE KEY (uk_user_email)`로 복원되는 반면, `group_member`의 `email`은 일반 `KEY (idx_gm_email)`로만 복원됩니다. 원본 `idx_gm_email`이 UNIQUE였는지 일반 인덱스였는지 확인이 필요합니다. 만약 UNIQUE였다면 롤백 후 데이터 무결성 문제가 발생할 수 있습니다.

- **해결 방안**: Step 2의 `SHOW INDEX` 결과에서 `Non_unique` 값을 확인하여, `idx_gm_email`이 UNIQUE(0)인지 일반(1)인지 기록하고 롤백 SQL에 정확히 반영합니다.
