## 변경 배경

이 커밋은 `GroupOnDemandSyncService` 클래스의 디바운스(debounce) 간격을 30,000ms에서 5,000ms로 단축하는 단일 변경입니다. 사용자가 마이페이지에서 그룹 정보를 수정한 후 그룹 화면으로 복귀했을 때, 기존 30초 대기 시간으로 인해 변경사항이 즉시 반영되지 않는 UX 문제를 해결하기 위한 조치입니다.

- **목적**: 그룹 정보 수정 후 복귀 시 반영 지연(30초)을 5초로 단축하여 사용자 경험 개선
- **도메인**: SSO/그룹 동기화 (비즈니스 로직)
- **변경 방향**: 중복 호출 방지(debounce) 효과는 유지하되, 대기 시간을 실사용 시나리오에 맞게 최적화

## [GOOD] 잘된 점

**1. 변경 의도가 주석에 명확히 문서화됨**

변경된 주석에는 다음과 같이 트레이드오프 사유가 구체적으로 기록되어 있습니다:

```java
/**
 * 화면 진입 시 group/list 연타(중복 호출)는 묶되, "mypage 수정 후 복귀" 는 반영되도록 짧게.
 * (30초는 수정 직후 복귀를 막아 반영 지연 발생 → 5초로 단축)
 */
```

이는 단순히 값을 바꾼 것이 아니라, 왜 30초가 문제였고 왜 5초가 적절한지에 대한 의사결정 근거를 남긴 것입니다. 유지보수자가 추후 이 값을 다시 변경해야 할 때 맥락을 이해할 수 있습니다.

**2. 변경 범위가 최소화됨**

단일 파일에서 단일 상수값만 변경하여 회귀(regression) 위험이 거의 없습니다. `DEBOUNCE_MS`는 `isDue()` 메서드에서만 참조되며, 해당 메서드는 다음과 같이 단순한 시간 비교 로직입니다:

```java
private boolean isDue(String spUserId) {
    Long last = lastSyncAt.get(spUserId);
    return last == null || (now() - last) >= DEBOUNCE_MS;
}
```

값이 작아질수록 `isDue()`가 `true`를 반환할 조건이 더 자주 충족되므로, 동기화가 더 자주 실행되는 방향으로만 동작합니다. 즉, 기존 로직의 정합성에 영향을 주지 않습니다.

**3. 메모리 기반 디바운스의 적절한 활용**

`ConcurrentHashMap<String, Long>`을 사용한 인메모리 디바운스는 멀티 인스턴스 환경에서 완벽하지 않지만, 주석에도 명시된 대로 "호출 줄이기 목적"이라는 원래 의도에 충실합니다. 5초로 단축되어도 여전히 동일 사용자의 연속 호출을 효과적으로 차단합니다.
