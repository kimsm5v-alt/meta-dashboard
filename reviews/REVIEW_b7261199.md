## 변경 배경

이 커밋은 LPA(잠재프로파일 분석) 결과의 정확성을 높이기 위해, 프론트엔드에서 자체 계산하던 유형 확률(`classification.allProbabilities`) 대신 **백엔드 API가 직접 제공하는 lpaTop1/2/3 확률 데이터를 우선 사용**하도록 변경한 것입니다.

- **목적**: 유형명(`lpaTypeName`)은 API 데이터를 우선 사용하면서도, 확률 데이터는 프론트엔드 재계산 결과를 사용하던 불일치 문제 해결. 카드/도넛 차트에서 유형명과 확률의 출처를 일치시켜 시각적 불일치 방지
- **도메인**: 비즈니스 로직 (데이터 변환 계층)
- **변경 방향**: 기존에는 `lpaTypeName`만 API 우선, 확률은 프론트엔드 재계산 -> 이제 유형명과 확률 모두 API 데이터를 우선 사용하도록 일원화

## [GOOD] 잘된 점

1. **명확한 우선순위 로직**: `data?.apiTypeProbabilities ?? classification.allProbabilities`로 API 데이터가 있으면 우선 사용, 없으면 프론트엔드 계산 결과로 fallback하는 구조가 명확하고 안전합니다. null 병합 연산자(`??`)를 사용하여 `apiTypeProbabilities`가 `null` 또는 `undefined`일 때만 fallback하므로, 빈 객체(`{}`)가 들어와도 의도치 않게 fallback되지 않습니다.

2. **일관된 데이터 정규화**: `buildApiTypeProbabilities` 함수 내에서 `normalizeLpaTypeName`을 재사용하여 유형명 정규화 로직이 일관되게 유지됩니다. `LPA_TYPE_NAME_MAP`에 정의된 별칭 매핑(예: `'안전균형형' -> '안전 균형형'`)이 API 데이터에도 동일하게 적용됩니다.

3. **방어적 null 처리**: `lpaTopEntry`가 없을 경우 `null`을 반환하고, `buildApiTypeProbabilities` 내부에서도 `!typeName || prob == null` 조건으로 안전하게 건너뜁니다. `prob`에 대해 `== null`을 사용하여 `undefined`와 `null`을 모두 처리하는 점이 적절합니다.

## [ISSUE] 개선이 필요한 부분

### Critical (즉시 수정 필요)

없음

### High (우선 수정 권장)

**1. `buildApiTypeProbabilities`의 확률값 스케일 검증 부재**

`classifyStudent`의 `allProbabilities`는 0~100 범위의 값(퍼센트)입니다. `normalize` 함수의 구현을 보면:

```typescript
const normalize = (logPosteriors: Record<string, number>): Record<string, number> => {
  const max = Math.max(...Object.values(logPosteriors));
  const expValues: Record<string, number> = {};
  for (const [type, lp] of Object.entries(logPosteriors)) {
    expValues[type] = Math.exp(lp - max);
  }
  const sum = Object.values(expValues).reduce((a, b) => a + b, 0);
  const probs: Record<string, number> = {};
  for (const [type, exp] of Object.entries(expValues)) {
    probs[type] = (exp / sum) * 100;  // 0~100 스케일
  }
  return probs;
};
```

`(exp / sum) * 100`으로 계산되므로 0~100 범위입니다.

반면, API의 `lpaTop1Probability`가 어떤 스케일(0~1 또는 0~100)로 오는지 코드상으로 확인할 수 없습니다. `buildApiTypeProbabilities`는 `Math.round(prob * 10) / 10`만 수행하므로, 만약 API가 0~1 스케일로 보내면 0~1 범위의 값이 그대로 `typeProbabilities`에 저장되어 UI 차트에 잘못 표시될 수 있습니다.

- **위치 (라인 번호)**: 183 (`buildApiTypeProbabilities` 함수 내 `Math.round(prob * 10) / 10`)
- **기존 코드**:
```typescript
result[normalized] = Math.round(prob * 10) / 10;
```
- **해결 방안**: **[수정 코드 제시 불가 - 문맥 파악 불충분]**
  - API 응답의 실제 `lpaTop1Probability` 값 범위를 확인할 수 없어 정확한 수정 코드를 제시할 수 없습니다.
  - **권장**: API 명세를 확인하여 `lpaTop1Probability`가 0~1 스케일인지 0~100 스케일인지 확인한 후, 필요시 `* 100` 변환을 추가하거나 주석으로 스케일을 명시하세요. 예를 들어 API가 0~1 스케일이라면 `Math.round(prob * 1000) / 10`으로 변환해야 합니다.

### Medium (개선 권장)

**1. `buildApiTypeProbabilities`의 타입 안전성 개선**

`entries` 배열의 타입을 `[string | null | undefined, number | null | undefined][]`로 명시하고 있으나, TypeScript가 튜플 타입을 추론할 수 있으므로 `as const`를 사용하면 더 간결해집니다.

- **위치 (라인 번호)**: 177-181
- **기존 코드**:
```typescript
const entries: [string | null | undefined, number | null | undefined][] = [
  [lpaTopData.lpaTop1TypeName, lpaTopData.lpaTop1Probability],
  [lpaTopData.lpaTop2TypeName, lpaTopData.lpaTop2Probability],
  [lpaTopData.lpaTop3TypeName, lpaTopData.lpaTop3Probability],
];
```
- **해결 방안 (수정 코드)**:
```typescript
const entries = [
  [lpaTopData.lpaTop1TypeName, lpaTopData.lpaTop1Probability],
  [lpaTopData.lpaTop2TypeName, lpaTopData.lpaTop2Probability],
  [lpaTopData.lpaTop3TypeName, lpaTopData.lpaTop3Probability],
] as const;
```

**2. `convertToAssessment`의 `apiTypeProbabilities` 옵셔널 처리 일관성**

`convertToAssessment`의 파라미터 타입에서 `apiTypeProbabilities`는 `Record<string, number> | null`로 정의되어 있으나, `fetchStudentFullAnalysis`의 반환 타입에서는 `Record<string, number> | null`로 동일합니다. `convertToAssessment` 호출 시 `data`가 `null` 또는 `undefined`일 수 있으므로 옵셔널 체이닝(`data?.apiTypeProbabilities`)이 이미 적용되어 있어 안전합니다. 현재 코드로 충분하며 추가 개선 불필요합니다.

## 주요 파일 분석

**변경 내용:**

**데이터 흐름 분석:**

1. **API 응답 수신**: `fetchStudentFullAnalysis`가 API를 호출하면 `rawResultData['lpaTop']`에서 `lpaTopMap`을 추출합니다. 이 맵은 `Record<string, LpaTopData>` 형태로, 키는 `"1"` 또는 `"2"`(회차)입니다.

2. **데이터 변환**: `parseRound` 내부에서 `lpaTopMap?.[String(ordNo)]`로 해당 회차의 LPA Top 데이터를 가져온 후, `buildApiTypeProbabilities(lpaTopEntry)`를 호출하여 `{유형명: 확률}` 형태로 변환합니다.

3. **우선순위 결정**: `convertToAssessment`에서 `const typeProbabilities = data?.apiTypeProbabilities ?? classification.allProbabilities;`로 API 데이터를 우선 사용합니다. 이때 `apiTypeProbabilities`가 `null`이거나 `undefined`이면 프론트엔드 계산 결과로 fallback합니다.

4. **UI 소비**: `typeProbabilities`는 `Assessment` 인터페이스를 통해 UI 컴포넌트와 AI 프롬프트 빌더(`dataHelperService.ts`)로 전달됩니다. `dataHelperService.ts`에서는 `data.typeProbabilities[data.predictedType]` 형태로 접근하여 확률값을 표시합니다.
