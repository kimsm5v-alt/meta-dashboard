[문의] /api/v1/users/batch — notFound 대신 maskedReason 사유 추가 제안

요청: 학심정(meta) RP · 대상: Auth(core-api) 회원 조회 API · 2026-06-18
한 줄. 현재 /users/batch는 동의 안 한/탈퇴/없는 사용자를 모두 notFound에 뭉뚱그려 줍니다. RP에서 "왜 정보가 안 왔는지"를 구분할 수 없어, 미동의 사용자에게만 안내 UI(툴팁)를 띄우거나 placeholder 문구를 정확히 분기할 수 없습니다. → 대상 사용자를 users에 포함하되 PII는 비우고, maskedReason(enum)으로 사유를 같이 내려주는 방향으로 수정 가능한지 문의드립니다.

1.현재 동작 (확인한 코드 기준)

UserService.getUsersByPublicIds(ids, tenantId, rpClientIdFilter):

  1. findAllByPublicUserIdInAndTenantId — status 필터 없음 (ACTIVE/SUSPENDED/WITHDRAWN 모두, hard purge 된 행만 제외)
  2. 호출자가 service AT + consent_required=true RP 면(=학심정) → isRpMember(userId, clientId) 로 필터
    isRpMember = existsByUserIdAndClientIdAndAgreementTypeAndRevokedAtIsNull(userId, clientId, SERVICE) (철회 안 된 active SERVICE 동의 보유 여부)
  3. notFound = 요청 id 중 최종 users 리스트에 없는 것 전부

그 결과 학심정 입장에서 notFound에는 아래 3가지가 구분 없이 들어옵니다:

사유설명
(a) 진짜 없음hard purge 완료 / 잘못된 id / 타 tenant
(b) 미동의행은 있으나 해당 RP에 SERVICE 동의 없음 (예: 그룹 동기화로 선제 생성됐지만 학심정 미로그인 학생)
(c) 탈퇴/연결끊기SERVICE 동의가 revoke됨 (탈퇴 30일 grace 중 행은 있으나 동의 철회)

현재 응답 형태

// 요청 (학심정 service AT)
POST /api/v1/users/batch
{ "publicUserIds": ["A_동의", "B_미동의", "C_탈퇴", "D_없음"] }

// 응답
{ "data": {
    "users": [ { "publicUserId":"A_동의", "name":"홍길동", "email":"...", ... } ],
    "notFound": [ "B_미동의", "C_탈퇴", "D_없음" ]   // ← 사유 구분 불가
} }

2.문제점

  • RP에서 (b)미동의 / (c)탈퇴 / (a)없음을 구분 못 함 → 학심정 현재 placeholder가 일괄 "(탈퇴 회원)" 로 떠서 미동의 학생에게도 '탈퇴'로 잘못 표기.
  • 요구사항: 그룹 멤버 리스트에서 미동의 학생만 이름/이메일 전체 마스킹 + 안내 툴팁("아직 검사 시작 안 한 학생, 최초 1회 로그인 안내…")을 띄워야 하는데, 사유를 모르니 미동의에만 정확히 분기 불가.

3.제안 — maskedReason enum 추가

정보 제공 안 하는 사용자도 users에 포함하되 PII(name/email 등)는 null로 비우고, 왜 비웠는지를 maskedReason으로 같이 내려줍니다. notFound는 진짜 없는 사용자만 남깁니다.

maskedReason의미PII 필드
NONE (또는 필드 생략)정상 (동의 회원)실제값
NOT_CONSENTED해당 RP 미동의null
WITHDRAWN탈퇴/동의 철회null
(NOT_FOUND)진짜 없음 — notFound 배열로 유지—

제안 응답 형태

// 응답 (제안)
{ "data": {
    "users": [
      { "publicUserId":"A_동의",   "name":"홍길동", "email":"hong@x.com", "status":"ACTIVE",    "maskedReason":"NONE" },
      { "publicUserId":"B_미동의", "name":null,    "email":null,        "status":"ACTIVE",    "maskedReason":"NOT_CONSENTED" },
      { "publicUserId":"C_탈퇴",   "name":null,    "email":null,        "status":"WITHDRAWN", "maskedReason":"WITHDRAWN" }
    ],
    "notFound": [ "D_없음" ]   // ← 진짜 없는 사용자만
} }

→ RP는 maskedReason으로 미동의/탈퇴/없음을 구분해 각기 다른 표시(툴팁/문구) 가능. 사유 추가는 enum 확장으로 흡수.

4.문의 사항

Q1. 호환성 — 가장 중요.
/users/batch는 공유 API입니다. 지금 미동의/탈퇴 사용자가 notFound에 들어가는 동작에 의존하는 기존 소비자(다른 RP / 어드민 도구 등)가 있나요? 제안대로 그들을 users로 옮기면(=PII는 null) 깨지는 곳이 있을지 검토 부탁드립니다.
대안: 기존 notFound는 유지하고 masked: [{publicUserId, maskedReason}] 배열을 추가하는 비파괴 방식도 가능 — 어느 쪽 선호하시는지?
Q2. enum 값/네이밍.
maskedReason 값 후보(NONE / NOT_CONSENTED / WITHDRAWN / NOT_FOUND) 합의 가능한지, Auth 내부 명명 규칙에 맞는 이름이 있는지.
Q3. 적용 범위.
/users/batch만 적용인지, 단건 GET /users/{publicUserId} · /users/lookup 도 동일 사유 모델로 맞출지.
Q4. 마스킹 필드 범위.
미동의 시 어떤 필드를 null로 줄지 — name/email/nickname/school*/profileImageUrl 전부 비우고, publicUserId/status/userType 같은 비PII 식별/상태값은 유지하는 게 맞는지.
Q5. consent_required=false RP.
mypage 등 first-party(consent_required=false)는 기존대로 전체 제공(필터·마스킹 없음) 유지 맞는지 확인.

5.참고 — 우리(학심정) 쪽 처리

  • UserInfoEnricher가 maskedReason을 멤버 DTO로 전파 → 그룹 멤버 리스트에서 NOT_CONSENTED면 전체 마스킹 + 안내 툴팁, WITHDRAWN이면 "(탈퇴)" 표기로 분기.
  • 이름/이메일 비저장(읽기 시점 enrich) 원칙은 그대로 — 평문 PII를 학심정 DB에 적재하지 않음.
