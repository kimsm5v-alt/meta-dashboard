# 학심정 × 슈퍼플랫폼 SSO 연동 — 오픈 일정 케이스별 대응 방안

---

안녕하세요, 공유해주신 통합 플랫폼 회원 체계 문서 잘 확인했습니다.

학심정 서비스에 SSO 통합 인증을 반영하는 건과 관련하여, 슈퍼플랫폼 Auth 시스템의 실제 구현 스펙(OAuth2 + PKCE, Auth Client SDK, BE 프록시 구조 등)을 사전 분석 완료한 상태입니다. 분석 결과를 토대로 오픈 일정에 따른 두 가지 케이스별 필요 작업과 일정 영향을 아래와 같이 정리드립니다.

---

## 케이스 1: 학심정이 슈퍼플랫폼보다 먼저 오픈하는 경우

학심정이 먼저 오픈한다면 슈퍼플랫폼 통합 로그인 시스템이 아직 준비되지 않은 상태이므로, 학심정은 **현재 자체 인증 체계(이메일/비밀번호 로그인)로 먼저 오픈**하고 이후 SSO를 붙이는 2단계 전략이 필요합니다.

### 1단계: 자체 인증으로 먼저 오픈

현재 학심정에 구현되어 있는 이메일 기반 회원가입, 로그인, 게스트 인증 체계를 그대로 사용하여 오픈합니다. 이 단계에서는 SSO 관련 작업이 전혀 포함되지 않으므로 추가 개발 일정은 없습니다. 다만, 이후 SSO 전환을 염두에 두고 아래 사항을 미리 준비해두어야 합니다.

첫째, 회원 테이블에 슈퍼플랫폼 사용자 ID를 저장할 컬럼을 미리 추가해 놓습니다. 이 컬럼은 당장은 비어 있지만, 나중에 SSO 전환 시 기존 회원과 슈퍼플랫폼 계정을 연결하는 데 사용됩니다. 컬럼 하나 추가하는 수준이라 기존 기능에 영향이 없습니다.

둘째, 로그인 페이지의 UI를 설계할 때 향후 SSO 로그인 버튼이 추가될 영역을 고려해두면 좋습니다. 당장 구현할 필요는 없지만, 레이아웃상 여유를 두면 전환 시 UI 변경이 수월합니다.

### 2단계: 슈퍼플랫폼 오픈 후 SSO 전환

슈퍼플랫폼이 오픈되면 학심정에 SSO 연동 작업을 진행합니다. 이 단계에서 필요한 작업은 다음과 같습니다.

**백엔드 작업으로는** 슈퍼플랫폼 Auth 서버와 통신하는 프록시 엔드포인트 4개를 새로 만들어야 합니다. 이것은 브라우저에서 직접 Auth 서버에 접근할 수 없는 비밀값(client_secret)을 서버 측에서 대신 전달해주는 역할입니다. 슈퍼플랫폼 측에서 샘플 코드를 제공하고 있어 구현 자체는 복잡하지 않습니다. 추가로 슈퍼플랫폼에서 발급한 JWT 토큰을 학심정 내부 사용자로 매핑하는 로직이 필요합니다. 기존 학심정 회원이 SSO로 처음 로그인하면 이메일 기준으로 자동 매칭해주는 방식으로 처리하면 별도의 데이터 이관 작업 없이 자연스럽게 전환됩니다.

**프론트엔드 작업으로는** 슈퍼플랫폼에서 제공하는 Auth Client SDK를 연동해야 합니다. 이 SDK가 로그인, 로그아웃, 토큰 관리, 세션 복구 등을 상당 부분 처리해주기 때문에 현재 학심정에 구현되어 있는 자체 로그인/토큰 갱신 로직을 SDK 기반으로 교체하는 작업이 됩니다. 로그인 페이지에 "슈퍼플랫폼으로 로그인" 버튼을 추가하고, 기존 이메일 로그인은 전환 기간 동안 보조 옵션으로 유지하다가 전환율이 충분해지면 제거합니다.

### 이 케이스에서 기획 측에 요청드리는 사항

이 케이스의 핵심 이슈는 **기존 회원의 SSO 전환 경험**입니다. 학심정을 자체 인증으로 먼저 오픈하면 그 기간 동안 가입한 회원들이 나중에 SSO로 전환해야 하는 상황이 발생합니다. 이때 사용자에게 어떤 안내를 보여줄지 기획이 필요합니다. 예를 들어, "기존 계정을 통합 플랫폼 계정과 연결하시겠습니까?" 같은 전환 유도 화면의 문구, 타이밍, 강제성 수준 등을 정해주셔야 합니다.

또한 **전환 기간 동안 자체 로그인과 SSO 로그인을 동시에 제공**할 것인지, 아니면 특정 시점에 자체 로그인을 차단하고 SSO만 허용할 것인지에 대한 정책도 미리 정해두면 개발 일정을 보다 정확히 산정할 수 있습니다.

SSO 전환 작업 자체는 슈퍼플랫폼 오픈 이후 **약 1.5~2주** 정도로 예상합니다. 다만 이 기간에는 슈퍼플랫폼 Auth 팀으로부터 서비스 등록(client_id/client_secret 발급)과 CORS 설정이 선행되어야 하므로, 슈퍼플랫폼 오픈 일정이 확정되면 **최소 1주 전에 Auth 팀과의 사전 조율**이 필요합니다.

## 케이스 2: 학심정과 슈퍼플랫폼이 동시에 오픈하는 경우

동시 오픈이라면 학심정을 처음부터 SSO 기반으로 오픈하는 것이므로, 자체 인증과 SSO를 병행 운영할 필요가 없어 오히려 기술적으로는 더 깔끔합니다. 다만, **슈퍼플랫폼 Auth 시스템이 개발 완료되어 안정적으로 동작하는 것이 전제 조건**입니다.

### 필요 작업

학심정 오픈 시점에 SSO가 유일한 인증 수단이 되므로, 위 케이스 1의 2단계 작업(BE 프록시 + FE SDK 연동)을 오픈 전에 모두 완료해야 합니다.

**백엔드에서는** Auth 서버 프록시 엔드포인트 4개 구현, 슈퍼플랫폼 JWT를 학심정 사용자로 매핑하는 로직, 게스트 토큰 발급 연동이 필요합니다. 현재 학심정에 구현된 자체 회원가입, 이메일 인증 코드 발송, 비밀번호 검증 등의 로직은 오픈 시점부터 사용되지 않게 되지만, 코드 자체를 급하게 삭제할 필요는 없고 SSO 인증 경로만 확실히 동작하면 됩니다.

**프론트엔드에서는** Auth Client SDK 기반의 인증 플로우를 전면 적용합니다. 자체 로그인 폼 대신 슈퍼플랫폼 로그인 페이지로의 리다이렉트가 기본 로그인 방식이 됩니다. SDK가 로그인, 로그아웃, 토큰 갱신, 세션 복구, 다른 탭 간 동기화를 모두 처리하므로 현재 자체 구현된 Silent Refresh 로직을 제거하고 SDK에 위임하게 됩니다.

**게스트(비회원) 참여 플로우도** 슈퍼플랫폼의 게스트 토큰 체계로 전환해야 합니다. 현재는 학심정이 자체적으로 게스트 JWT를 발급하지만, SSO 체계에서는 Auth 서버가 게스트 토큰을 발급하고 학심정 BE는 도메인 검증(초대코드 확인, 게스트 등록 등)만 담당합니다. 기존 초대코드 기반의 게스트 참여 플로우는 유지하되, 토큰 발급 경로만 Auth 서버 경유로 변경됩니다.

### 이 케이스에서 기획 측에 요청드리는 사항

동시 오픈의 경우 가장 중요한 것은 **개발 일정의 의존 관계**입니다. 학심정의 SSO 연동 개발을 시작하려면 슈퍼플랫폼 Auth 서버가 최소한 개발 서버에서 동작하고 있어야 하고, 학심정용 서비스 등록(client_id/client_secret)이 완료되어 있어야 합니다. 만약 슈퍼플랫폼 Auth 서버의 개발이 아직 진행 중이라면 학심정 측에서 연동 개발을 시작할 수 없으므로, **슈퍼플랫폼 Auth 서버의 개발 완료 시점을 확인**해주셔야 합니다.

학심정 측 SSO 연동 개발 기간은 **약 1.5~2주**로 예상하며, 이후 통합 테스트에 **약 1주**가 추가로 필요합니다. 따라서 동시 오픈을 목표로 한다면 최소 오픈 **3주 전에는 Auth 서버가 개발 환경에서 사용 가능**한 상태여야 합니다.

추가로, 동시 오픈 시 학심정에 처음 접근하는 사용자는 반드시 슈퍼플랫폼에서 먼저 회원가입을 해야 합니다. 이 경우 학심정 서비스 화면에 진입하기 전에 슈퍼플랫폼 회원가입과 서비스 연동 동의 화면을 거치게 되는데, 이 과정에서 학심정에서 추가로 수집해야 하는 정보(성별, 학교명, 학교급, 학년/반/번호 등)를 **어느 시점에 입력받을지** 기획이 필요합니다. 슈퍼플랫폼의 서비스 연동 동의 화면 직후에 학심정 자체 추가 정보 입력 화면을 넣을 것인지, 아니면 서비스 진입 후 최초 이용 시 입력받을 것인지에 따라 화면 설계와 개발 범위가 달라집니다.

## 공통 사항: Auth 팀과의 사전 조율이 필요한 항목

어느 케이스든 아래 항목은 슈퍼플랫폼 Auth 팀과 사전 조율이 필요하며, 기획 측에서 연결해주시거나 일정을 잡아주시면 감사하겠습니다.

1. **서비스 등록 요청**: 학심정 서비스명, 콜백 URL(환경별), 담당자 정보를 전달하면 Auth 팀에서 client_id와 client_secret을 발급합니다. 이 과정이 선행되지 않으면 개발 착수가 불가합니다.

2. **CORS 도메인 등록**: 학심정의 프론트엔드 도메인을 Auth 서버의 허용 목록에 추가해야 합니다. 개발 환경(localhost)과 운영 환경 각각 등록이 필요합니다.

3. **서비스별 추가 정보 수집 정책**: 슈퍼플랫폼 공통 회원 정보(이메일, 이름, 역할)와 별도로 학심정이 추가 수집하는 정보(성별, 학교, 학년 등)의 입력 시점과 화면 기획이 필요합니다.

4. **게스트(비회원) 참여 정책**: 현재 학심정의 초대코드 기반 게스트 참여와 슈퍼플랫폼의 QR코드 진입 방식을 어떻게 통합할지, 또는 기존 방식을 유지할지 결정이 필요합니다.

| 전제 조건 | 특별히 없음 (오픈 후 작업) | Auth 서버 개발 완료 + 서비스 등록 완료 |
| 기존 회원 전환 | 필요 (SSO 전환 유도 기획 필요) | 불필요 (처음부터 SSO) |

일정이 확정되면 구체적인 작업 계획을 수립하겠습니다. 추가 확인이 필요한 사항이 있으시면 말씀해주세요.
